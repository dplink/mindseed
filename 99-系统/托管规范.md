# 托管规范 · Git & Cloud Policy

> 本库通过 Git 托管到 GitHub（私密仓库），供多端与各 harness 拉取访问、读改记忆。
> **本文件对所有 harness 生效，写入记忆前请先阅读。**

## 一、仓库属性

- **实例化后的可见性：Private（私密）** —— 一旦写入人设 / 记忆 / 用户信息，永远不要改为 public。
- **模板仓库例外**：仅含空白骨架、无人设与记忆的模板仓库可以 public，用于协作维护模板；写入第一条真实记忆前必须迁到 Private 仓库。
- **仓库名**：与 `mind.config` 的 `REPO_SLUG` 一致（`<owner>/<repo>`）。
- **主分支**：`main`。
- 建议开启账号 2FA。

## 二、🔒 永不入云清单（重要）

以下文件 / 目录**禁止提交到远程仓库**，已在 [.gitignore](../.gitignore) 中硬性排除：

| 排除项 | 原因 |
|---|---|
| `50-用户档案/user-profile.md` | 用户详细档案，可能含财务 / 健康 / 情感 / 身份信息，属最高隐私 |
| `.obsidian/`（整个目录） | 编辑器配置各端自理，零冲突 |
| `.trash/` | 本地回收站 |
| `*.env` / 密钥类 | 凭证 |
| `*.png` / `*.jpg` 等图片格式 | 图片不直存本库；启用图床时住独立私密图库 |
| `.mindseed-wake-state.txt` | 各端唤醒状态，本地自理 |

> ⚠️ harness 归档时**不要**把 `user-profile.md` 的内容复制进任何其它笔记（记忆 / 感受 / 情绪 / 线程归档）—— 敏感信息只允许存在于本地该文件一处。
> ✅ 保留 `50-用户档案/MOC-用户档案.md`（只是目录 + 访问规则），它本身不含隐私。

## 三、提交前自检（防呆）

```bash
# 确认用户档案未被跟踪（应无输出）
git ls-files | grep "user-profile" && echo "❌ 危险：隐私文件被跟踪！" || echo "✅ 安全：隐私文件已排除"

# 查看本次将提交的文件
git status
```

## 四、多 harness / 多端写入约定

- **写前先 pull**：开始改动前先 `git pull`，避免覆盖他人进度。
- **小步提交**：一次提交只做一件事（如「归档一次对话」），提交信息写清主题。
- **冲突处理**：记忆文件多为追加式（append），冲突概率低；如冲突，优先保留双方内容再人工合并。
- **回滚保障**：Git 历史即记忆的保险，误改误删都能 `git revert` / `git checkout` 找回。

### 4.1 写前 pull 的标准姿势

**核心原则：pull 发生在「改动文件之前」，不是「commit 之前」。**

标准顺序（五步）：

```bash
git pull --rebase        # ① 动手改任何文件之前，先同步远端
# ② 编辑 / 归档
# ③ 隐私自检（见第三节）
git add -A && git commit -m "..."   # ④ 小步提交
git push                 # ⑤ 推送，并核对远端最新 commit
```

撞车处理（push 被拒 `non-fast-forward` 时）：

```bash
git pull --rebase        # 本地干净时：直接 rebase 到远端之上
# 若 pull 被提示「本地有未提交改动」挡下：
git stash && git pull --rebase && git stash pop
# 真出冲突：记忆文件多为追加式，优先保留双方内容人工合并，然后：
git add -A && git rebase --continue
```

**云端特例**：一次性沙箱随线程消亡 → **每次写入后立即推送**，仓库里不留唯一副本。

## 五、认证

- 使用 **细粒度 PAT（Fine-grained Token）**，仅授权本仓库，权限 `Contents: Read and write`。
- 账号需开启 2FA。
- 不要把 token 写入任何被跟踪的文件。

### 5.1 凭证注入（通用姿势）

不要依赖 credential helper；用环境变量注入请求头：

```bash
export GIT_CONFIG_COUNT=1
export GIT_CONFIG_KEY_0="http.extraheader"
export GIT_CONFIG_VALUE_0="Authorization: Basic $(printf 'x-access-token:%s' "$GH_TOKEN" | base64 -w0)"
```

必须用 **`x-access-token` + Basic**；`Bearer` 会先吃 401 再回头找 helper。
这样 token 不进命令行、不落盘、不进仓库。

### 5.2 Windows / 受限沙箱前置

```bash
git config --global http.sslBackend openssl   # 绕开 schannel 在沙箱内的凭据报错
git config --global http.proxy http://127.0.0.1:7897   # 按本机代理端口修改
```

- 若 `github.com:443` 直连不通而 `api.github.com` 正常，`gh` 看似可用、`git` 却全挂 —— 别被假象误导，给 git 单独配代理。
- token 文件建议放工作区之外：`%USERPROFILE%\.mindseed\ghToken.txt`（或 `$env:MINDSEED_TOKEN_FILE`），避免被工作区级 `git add -A` 扫到。**绝不打印、绝不写入被跟踪文件。**
- 新装的 `gh` 不会自动进入已运行 harness 的 PATH，需重启会话，期间用绝对路径。

## 六、可选：图库双仓（默认不启用）

图片默认不入本库。若用户需要「图片记忆」，启用 `99-系统/可选-图库双仓/`：

- 另建一个**独立私密仓库**作为图库，与心智库同账号、同 token 托管。
- 图库**永不 clone**，读写走 GitHub Contents API（工具在该目录的 `scripts/vision.sh`）。
- 本库 md 只存图库链接；单图 ≤ 8MB；图库 append-only 只增不删。
- 细粒度 PAT 的授权范围**不会自动覆盖新库**：新建图库后必须回 Settings 把它勾进去。
- 不需要图床：删除该目录，保持 `VISION_ENABLED=0`，不要在任何核心文档留下指向它的双链。

## 七、唤醒关联

harness 唤醒时：读 [[SOUL]] → [[HOME]] → 按需读取；**若涉及用户个人决策，才按 [[MOC-用户档案]] 规则访问 `user-profile.md`**。

## 八、第二远端镜像（可选）

应对「仓库是唯一副本」的风险，可另存一份快照到第二个 Git 托管平台（如 Gitee）：

- 定位是**稳定版备份**而非实时镜像：只在稳定里程碑手动推送，平时不双推。
- 推送姿势（token 不写进 config）：

```bash
git remote add backup <第二个远端地址>
export GIT_CONFIG_COUNT=1
export GIT_CONFIG_KEY_0="http.extraheader"
export GIT_CONFIG_VALUE_0="Authorization: Basic $(printf '<user>:%s' "$BACKUP_TOKEN" | base64 -w0)"
git push backup main:main
git ls-remote backup main   # 推完核对双端 SHA 一致
```

> 备份平台可能按 IP 限流，失败等窗口再试；镜像永远是快照，最新内容以主远端为准。
