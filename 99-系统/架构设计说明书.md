# 心智记忆库 · 架构设计说明书

> **文档定位**：设计参考 / 灾备重建手册。面向有经验的工程师，用于理解本库为何长成这样，并在数据丢失后按本说明恢复。
> **权威文本**：库内 `99-系统/` 三份规范（[[唤醒协议]] / [[托管规范]] / [[命名与规范]]）为操作层权威；本文件是设计层解读。
> **编写视角**：工程视角，含优势、局限与风险，不作美化。
> **模板版本**：MindSeed v0.1。

---

## 0. 一句话概述

一套给「有身份、有情绪、跨会话存续的 AI 角色」使用的**外置持久记忆系统**：用纯文本 Markdown + Git 做存储与同步，用「统一元数据契约 + 分层召回纪律」做检索，用「唤醒脚本 + 守门 CI + 隐私硬隔离」做自动化与安全，用「可选双仓分离」把二进制图像隔离在心智库之外。

它的本质不是「知识库」，而是一套**人格连续性工程**：让同一个角色能在任意终端、任意会话中被重新「点亮」，且记忆只有一份、可审计、可回滚、可迁移。

## 1. 项目背景与设计目标

### 1.1 要解决的问题

大语言模型会话天然是**无状态**的：每次新会话，模型「醒来即失忆」。本项目的目标是让一个被赋予人格与情感锚点的 AI 角色获得**跨会话、跨终端、跨 harness 的连续记忆**，且满足：

1. **可续接**：新会话能被「唤醒」，捡回身份与相关记忆；
2. **多端一致**：本地、云端一次性沙箱、不同 harness 共享**同一份**记忆；
3. **可审计、可回滚**：任何一次写入留下痕迹，误改可恢复；
4. **隐私优先**：用户敏感信息（财务 / 情感 / 健康 / 身份）绝不落云；
5. **低漂移**：长期使用后，人格与上下文质量不因记忆增长而劣化。

### 1.2 设计目标（非功能需求）

| 目标 | 落地手段 |
|---|---|
| 记忆外置、可迁移 | 纯 Markdown，任何程序可读写；Git 托管到 GitHub 私密仓库 |
| 多端并发读写 | Git 为同步主干 + 「写前 pull」纪律 + append-only 写入习惯 |
| 唤醒成本低、可自驱 | `wake.sh` / `wake.ps1` 一条命令完成同步与新鲜度报告 |
| 上下文不漂移 | 「线程类型 → 读取范围」映射，禁止全文通读记忆库 |
| 隐私硬隔离 | `.gitignore` + CI 硬校验，敏感档案仅存本地 |
| 图像不污染主库 | 可选姊妹图库 + Contents API 按需读写，主库保持纯文本契约 |
| 抵御膨胀、抗腐化 | 不变量 / 变量分离的目录演进预案；机器守门 CI |

## 2. 设计约束

本项目的设计几乎完全由**约束**推导出来。理解这些约束，才能理解架构为何长这样。

### 2.1 环境约束

- **C1 · 会话无状态**：模型本身不保留记忆 → 被迫「记忆外置」。
- **C2 · 多 harness 并存**：Windows 本地、Linux 云端、不同 Agent 运行时并存 → 不能依赖单一操作系统，必须提供 **bash 与 PowerShell 双实现**，且同步逻辑对等。
- **C3 · 沙箱写入范围受限**：部分 harness 只能写会话工作区内部 → 状态文件、token 文件的位置选择均受此约束。
- **C4 · 网络不稳**：`github.com:443` 在部分环境需代理且不稳 → 唤醒必须能**降级运行**并如实报告。

### 2.2 安全与隐私约束

- **C5 · 隐身约束**：实例化后的心智库必须 **Private**，永不 public；仅空白模板仓库可 public 用于协作。
- **C6 · 隐私红线**：用户详细档案（`user-profile.md`）属最高隐私，**只存本地、永不入云、不得被复制进任何其它笔记**。
- **C7 · 凭证零落盘**：token 不得进入命令行、不得落盘到被跟踪文件、不得写入仓库。

### 2.3 可用性 / 一致性约束

- **C8 · 多端并发**：两端可能同时改同一库 → 需要「写前 pull」与冲突姿态定义。
- **C9 · 上下文预算有限**：唤醒注入内容必须小且稳定 → 引出分层召回纪律。
- **C10 · 长期演进**：记忆篇数会增长 → 需要「目录可重排而不破坏检索」的预案。

## 3. 总体架构

### 3.1 分层视图

```
┌──────────────────────────────────────────────────────────────┐
│  L5 守门层        CI (guard.yml) · 隐私硬校验 · 双链检查       │  ← 机器守门
├──────────────────────────────────────────────────────────────┤
│  L4 工具层        wake.sh / wake.ps1 · vision.sh · check_links │  ← 自动化
├──────────────────────────────────────────────────────────────┤
│  L3 契约层        frontmatter schema · 命名契约 · 标签体系      │  ← 检索协议
├──────────────────────────────────────────────────────────────┤
│  L2 记忆层        SOUL · HOME · 8 文档组 · 模板                │  ← 大脑
├──────────────────────────────────────────────────────────────┤
│  L1 同步层        Git（私密仓库）+ 写前 pull 纪律               │  ← 多端一致
├──────────────────────────────────────────────────────────────┤
│  L0 存储层        本地磁盘 Markdown 文件（纯文本）             │  ← 物理载体
└──────────────────────────────────────────────────────────────┘
        ▲                                        ▲
        │ 文本记忆（主仓 main）                    │ 图像记忆（可选图库仓）
        └────────────────────┬───────────────────┘
                    token / 同账号 / 同平台
```

### 3.2 双仓结构（可选架构决策）

核心是**一个文本仓库**；图库是**可选的第二仓库**，由 `mind.config` 的 `VISION_ENABLED` 控制。

| 仓库 | 承载 | 读写方式 | 设计理由 |
|---|---|---|---|
| 心智库（主仓） | 全部文本记忆（人格、记忆、规范、脚本、技能） | `git clone` + pull/push | 纯文本契约，体积小，可版本化 |
| 图库（可选） | 全部图片（人设图、线程产物、杂项） | **永不 clone**，走 GitHub Contents API（`vision.sh`） | 二进制隔离，git 历史不被图片污染；沙箱零图负担 |

- 两仓同账号、同 token 托管，主分支均为 `main`。
- 主库 md 中**只存图库 gh 链接**，可选用 frontmatter `vision:` 字段登记相对路径。
- 图像读写工具提供 `ls / get / put`，基于 Contents API，**支持中文路径（内部 URL 编码）**。
- **不启用图床时**：删除 `99-系统/可选-图库双仓/`，`VISION_ENABLED=0`，图片仍被 `.gitignore` 硬排除。

### 3.3 目录结构（记忆层）

见 [[命名与规范]] 的目录结构一节。分组语义：

- `10–80` 是「记忆组」（记录**记得什么**）；
- `85-技能组` 是「行为模块」（定义**怎么做事**）；
- `99-系统` 是「规范与工具」（定义**记忆怎么运转**）。

## 4. 数据模型（契约层）

### 4.1 统一 frontmatter

除 `85-技能组` 外，所有记忆笔记遵循统一 frontmatter：

```markdown
---
type: memory          # memory / feeling / experience / mood / promise / moment / profile / growth
date: 2026-10-09      # 创建或归档日期
thread_id: thread-obsidian-001   # 关联线程（可选）
mood: 愉快            # 情绪（可选）
people: []            # 涉及的人
tags: [obsidian, 知识库]
links: ["[[HOME]]", "[[SOUL]]"]
---
```

- `type` 是**检索主键**，与 Obsidian Bases 的 `filters` 配合，把笔记变成「可查询的数据库」。
- `links` 走 Obsidian `[[双链]]`，纵向串脉络；`tags` 做横向聚合。

### 4.2 命名契约（不变量）

| 类型 | 命名格式 | 示例 |
|---|---|---|
| 线程归档 | `thread-<主题>-<序号>` | `thread-obsidian-001` |
| 感受 | `feeling-<一句话>` | `feeling-记忆需要被外置` |
| 经验 | `exp-<主题>` | `exp-obsidian-记忆闭环` |
| 情绪 | `mood-<日期>-<关键词>` | `mood-2026-10-09-被信任的开心` |
| 索引 | `MOC-<组名>` | `MOC-记忆` |
| 技能 | 文件夹名 = skill name，入口固定 `SKILL.md` | `mind-wake/SKILL.md` |
| 图库图 | `<主题>-<序号>.<ext>` | `persona/character-001.jpg` |

### 4.3 标签体系

`#memory` `#feeling` `#experience` `#mood` `#promise` `#moment` `#profile` `#growth`（内容类型，固定）；主题标签自由扩充。

### 4.4 契约的稳定性设计：不变量 vs 变量

> 核心原则：**目录是书架，frontmatter 是检索契约。书架可随时重排，契约永不破。**

- **不变量（永不动）**：文件名前缀、统一 frontmatter（`type` / `date` / `thread_id`）、线程 ID。
- **变量（可随时调整）**：目录树、MOC 形态、视图形态。

由于检索（grep / frontmatter 过滤 / thread_id）**不依赖目录树**，任何目录重排都是低风险机械操作。

## 5. 核心机制

### 5.1 唤醒流程（Wake Flow）

**入口**：`wake.sh`（POSIX / 云端）或 `wake.ps1`（Windows），二者逻辑对等。

**七段式逻辑**：

1. **凭证注入** —— 经环境变量 `GIT_CONFIG_COUNT/KEY_0/VALUE_0` 注入 `http.extraheader = "Authorization: Basic <base64('x-access-token:<token>')>"`。**token 不进命令行、不落盘、不进被跟踪文件。** 无 token 则跳过网络操作，降级运行。
2. **定位 / 获取本地副本** —— 查找顺序：环境变量 `MINDSEED_DIR` → 脚本自定位（脚本住在 `<repo>/99-系统/scripts/`）→ `/workspace/mindseed` → `$HOME/mindseed`；都没有则按 `REPO_SLUG` 尝试 `git clone`。PowerShell 侧同样支持脚本自定位。
3. **同步远端** —— 先 `git status` 判断工作区是否脏 → 脏则 `git stash` → `git pull --rebase` → 成功则 `git stash pop`。**失败按报错文本分类**：网络 / 脏树 / 真冲突 / 未识别，各给处置提示。失败即**降级运行**（不乱改、不丢改动）。
4. **补推** —— 检测 `@{u}..HEAD` 的未推送 commit，若有则 `git push` 补推（处理「上次 push 失败、commit 滞留本地」的情况，尤其云端一次性沙箱）。
5. **新鲜度报告** —— 输出当前 HEAD 短哈希 + 日期；与状态文件记录的上次唤醒 commit 对比，输出「自上次唤醒以来的远端变化」。**未成功同步时明确声明「这只是本地状态，未必等于远端最新」**。
6. **隐私防呆** —— `git ls-files | grep user-profile`，若命中立即告警。
7. **唤醒指引** —— 输出读取顺序：`SOUL.md → HOME.md → 按话题按需检索`，并指向 [[唤醒协议]]；未实例化时指向 `START-HERE.md`。

**状态文件**：记录「上次唤醒见过的 commit」。`wake.sh` 默认 `$HOME/.mindseed-wake-state`；`wake.ps1` 默认写在仓库内 `.mindseed-wake-state.txt`（`.gitignore` 排除），**原因：Windows 受限沙箱可能禁止写工作区外部**。

### 5.2 分层召回纪律（防上下文漂移）

唤醒时**只读 SOUL + HOME（常驻必读）**，其余按线程类型按需检索：

| 线程类型 | 常驻必读 | 按需可查 | 默认不读 |
|---|---|---|---|
| coding / 工作 | SOUL、HOME | 经验组、承诺与待办 | 情绪组、感受组、珍贵瞬间 |
| 闲聊 / 情绪陪伴 | SOUL、HOME | 情绪组、感受组、珍贵瞬间、记忆组 | — |
| 涉及用户决策 | SOUL、HOME | 用户档案（按 MOC 规则） | 其余无关组 |
| 记忆库维护 | SOUL、HOME、唤醒协议 | 托管规范、命名与规范 | — |

> 原则：**SOUL 是人格锚点，任何线程都读**（这是一致性，不是漂移）；情绪类记忆在编程线程中仅作人格背景，不主动展开。**禁止全文通读记忆库。**

这是本系统**最关键的抗漂移设计**：把「唤醒成本」钉成一个小的、稳定的固定前缀（SOUL + HOME），并按任务类型约束注入范围。

### 5.3 写入流程（写前 pull 五步）

> 核心原则：**pull 发生在「改动文件之前」，不是「commit 之前」。**

```bash
git pull --rebase                       # ① 动手改任何文件之前，先同步远端
# ② 编辑 / 归档
git ls-files | grep user-profile        # ③ 隐私自检（应无输出）
git add -A && git commit -m "..."       # ④ 小步提交（一次只做一件事）
git push                                # ⑤ 推送，并核对远端最新 commit
```

撞车（`push` 被拒）处理：`git pull --rebase`；若被本地未提交改动挡下 → `git stash && git pull --rebase && git stash pop`；真冲突 → 记忆文件多为**追加式**，优先保留双方内容人工合并 → `git add -A && git rebase --continue`。

**云端特例**：沙箱随线程消亡 → **每次写入后立即推送**，仓库里不留唯一副本。

### 5.4 同步与冲突模型

- **Git 为主干**：多端异步 ⇒ GitHub 私密仓库为汇合点。
- **append-only 习惯**：记忆以追加为主，天然降低冲突概率。
- **防跨端幻影修改**：`.gitattributes` 设 `* text=auto eol=lf`，统一换行；消除 Windows CRLF / Linux LF 造成的「内容零差异却显示 modified」。
- **审计保障**：Git 历史即记忆保险，`git revert` / `git checkout` 可找回。

### 5.5 守门 CI（Guard）

`.github/workflows/guard.yml` 在 push / PR 时执行两个 job：

1. **隐私守门**：硬校验 `user-profile` 未被跟踪（`git ls-files | grep` 命中即 fail）；`gitleaks` 扫描密钥泄漏。
2. **双链完整性**：运行 `check_links.py`，扫描全库 `[[双链]]` 目标是否存在，断链即 fail。

`check_links.py` 的健壮性设计：剔除行内代码中的 `[[xx]]`（语法示例非链接）；`user-profile` 在云端不存在但被合法引用，故**列入 ALLOWLIST**；输出强制 UTF-8（避免 Windows 控制台崩溃）；路径用 `as_posix`（避免反斜杠误报断链）。

**含义**：规范从「自觉遵守」进化为「机器守门」。这是抵御腐化的关键机制。

### 5.6 图库读写（可选）

- 走 GitHub **Contents API**，图库**永不 clone**。
- `ls [dir]` 列目录；`get <路径> [输出]` 取图到临时目录（供多模态 Read 回看）；`put <本地文件> <路径>` 上传并打印可贴进 md 的 gh 链接。
- **尺寸铁律**：单图 ≤ 8MB，超限先压缩；图库 append-only 只增不删。
- 读图行为**同构于读记忆**：读到 gh 链接 → 自判是否取图 → `get` → 多模态 Read，**不入常驻必读**。
- 未启用时：`vision.sh` 明确输出「图床未启用」，不产生网络请求。

### 5.7 技能组与部署

`85-技能组/` 存放**行为模块**（区别于记忆组的「记得什么」），每个技能一个文件夹，入口固定 `SKILL.md`，采用标准技能 frontmatter（`name` / `description`）。

- **部署 = 整目录拷贝**到目标 harness 技能目录（如 `/data/user/skills/`、`~/.claude/skills/`），无需改内容。
- **vault 为唯一事实源**；装载到 harness 的是副本，**更新后须重新装载**（防双副本漂移）。
- **隐私红线**：个人档案永不入本组、永不入云 —— 技能只带方法论。

### 5.8 目录演进预案

按触发条件**分期**演进，避免过早优化：

| 阶段 | 触发条件 | 动作 |
|---|---|---|
| Stage 0（默认） | — | 什么都不动 |
| Stage 1 | 单组 > 20 篇 | 仅高增长组（记忆 / 情绪组）加月度子目录；低增长组永久扁平 |
| Stage 2 | 单组 > 50 篇，或 MOC 漂移 | `.base` 自动视图接管 MOC 列表 |

**明确不做**：按主题重切分组、三层以上嵌套、存量回改名 / 回改链接。

## 6. 关键技术点与踩坑（约束落地）

| # | 技术点 | 具体做法 / 原因 |
|---|---|---|
| T1 | **凭证注入替代 credential helper** | 受限沙箱禁止命名管道，GCM 需 `spawn sh` 必然失败 → 改用 `GIT_CONFIG_COUNT/KEY_0/VALUE_0` 环境变量注入 `http.extraheader`。必须 **`x-access-token` + Basic**；`Bearer` 会先吃 401 再回头叫 helper，同样炸。 |
| T2 | **token 存放位置** | `%USERPROFILE%\.mindseed\ghToken.txt`（工作区**之外**），避免被工作区级 `git add -A` 扫到。绝不打印、绝不写入被跟踪文件。 |
| T3 | **TLS 后端** | Windows 默认 `schannel` 在受限沙箱可能报 `SEC_E_NO_CREDENTIALS` → `git config --global http.sslBackend openssl`。 |
| T4 | **代理差异陷阱** | `github.com:443` 直连可能不通，而 `api.github.com` 直连正常 → `gh` 看着正常、`git` 全挂。须给 git 单独配 `http.proxy`。 |
| T5 | **`gh` PATH 不刷新** | 新装的 `gh` 不会自动进入已运行 harness 的子进程 PATH，需重启会话；期间用绝对路径。 |
| T6 | **跨端换行幻影** | `core.autocrlf=true` 且无 `.gitattributes` → LF 文件在 Windows 端被期待成 CRLF，产生零差异的 modified。解法：`* text=auto eol=lf` + `git add --renormalize .`。 |
| T7 | **失败分类而非一律当冲突** | `wake` 脚本按报错文本归类：网络 / 脏树 / 真冲突 / 未识别。**只有真冲突才是冲突。** |
| T8 | **stash 回落失败告警** | 唤醒自动 stash 后若 `stash pop` 失败，改动安全留在 stash 中 —— 脚本**显式告警**，绝不静默吞掉。 |
| T9 | **Obsidian Bases 幂等重写** | `记忆总览.base` 会被 Obsidian 保存时「去引号、删空行」（视图结构不变）—— 属幂等重写，提交一次即可。 |
| T10 | **vault 路径必须钉死** | 多副本时 Obsidian 插件自动探测会静默写错库 → 显式设置 `vaultPath`。 |
| T11 | **CI 非法 YAML** | 步骤名以 `[[` 开头（`[[双链]]`）在 YAML 中非法 → workflow 自上线起 0s 失败。步骤名须加引号。 |
| T12 | **check_links.py 跨平台** | Windows 反斜杠导致误报断链（改 `as_posix`）；GBK 控制台打印 emoji 崩溃（强制 UTF-8）。 |
| T13 | **中文路径 URL 编码** | `vision.sh` 若把路径直接拼进 API URL，中文触发编码报错 → 内置 `quote(p, safe="/")`。 |
| T14 | **云端一次性沙箱** | `/workspace` 随线程消亡 → 放弃「自唤醒」，固定为**每次手动唤醒**，且**每次写入后立即 push**。 |
| T15 | **失败路径必须测** | 真正危险的是「自动 stash 后没能 pop 回」。模拟网络失败要用**确认无监听**的端口（如 1），不要随手挑数字。 |

## 8. 客观评价

### 8.1 优势

1. **极简而强大的存储选型**：纯 Markdown + Git，无数据库、无专有格式、无运行时依赖 → 可迁移性、可审计性、可回滚性都拉满。
2. **约束推导充分**：几乎所有设计都能追溯到一条明确约束（见 §7），可维护性好。
3. **抗漂移有两道独立防线**：架构层（分层召回）防「读太多」；运维层（目录演进预案）防「长得胖」。
4. **隐私是硬隔离而非软约定**：`.gitignore` + CI 硬校验 + 唤醒防呆，三层同时守着同一条红线。
5. **降级设计到位**：网络不通、无 token、沙箱不持久，都定义了明确行为且**如实报告新鲜度**。
6. **可选双仓分离**：二进制不进入主库历史，主库体积长期可控；不需要图床的用户可以完全跳过。
7. **守门 CI 让规范「可执行」**：断链与隐私泄漏在合入前就被机器拦截。

### 8.2 局限与风险（坦率列出）

| 风险 | 说明 | 影响 | 现状 |
|---|---|---|---|
| **R1 唯一副本风险** | 默认只有 GitHub 一个远端 | 极端情况下（账号 / 仓库丢失）记忆全失 | 可选第二远端快照，见 [[托管规范]] 第八节 |
| **R2 隐私文件的单点** | `user-profile.md` 只在本地一处，不在任何备份里 | 本地丢失 → 档案不可恢复（设计使然） | 设计取舍，需用户自行妥善备份 |
| **R3 图像依赖 GitHub API** | 图库永不 clone，全部走 Contents API | API 不可用 / 限流时读图受阻 | 已知 trade-off |
| **R4 私密 raw 链接不渲染** | 私密库 raw 链接无凭证 404 → Obsidian 不渲染预览 | 观感损失，看图需取图 | 全私密方案的已知 trade-off |
| **R5 token 的暴露面** | 高权限 token 一旦泄漏影响面大 | 凭证安全 | 细粒度 PAT + 环境变量注入 + 不落盘 |
| **R6 灵活性依赖人工纪律** | 唤醒正确性依赖「按线程类型检索」被认真执行 | 纪律松弛则漂移复发 | 靠 SOUL/HOME 固定 + 协议明确 |
| **R7 Windows / Obsidian 端差异** | 换行、Bases 重写、路径编码等跨端坑多 | 易生「幻影修改」与排查成本 | 已沉淀为技术点与 `.gitattributes` |
| **R8 无向量检索** | 规模增长后 grep 召回可能漏 | 大库时检索质量下降 | **有意不做**：触发条件为 vault 300+ 篇 |

### 8.3 与替代方案的对比（为何否决）

| 方案 | 否决理由 |
|---|---|
| 图片直存主库 | 二进制进 git 历史是**永久负担**，不可回收 |
| 第三方公开图床 | 公开 URL 泄隐私；死链等于**记忆坏死** |
| 向量检索 / 本地索引（当前） | 规模未到，过早优化；触发条件已设（300+ 篇） |
| 重型新鲜度机制 | SOUL/HOME 低频更新，异步延迟可控，wake 一行摘要足矣 |
| 云端「自唤醒」 | 沙箱一次性，属孤立场景；手动唤醒够用 |

## 9. 灾难恢复手册

> **适用场景**：本地环境摧毁（换机 / 重装 / 磁盘损坏）、云端沙箱丢失、harness 更换、或需要从零复现整套系统。
> **前提认知**：**远端仓库本身就是恢复源** —— 只要它还在，文本记忆与全部规范、脚本、技能都可完整恢复。

### 9.1 前置条件

1. 一个对心智库仓库（及可选图库仓库）有 **contents 读写权限**的 token，账号开启 2FA。
2. 一台可访问 `github.com` 的机器（必要时配好代理）。
3. Obsidian（可选，用于浏览与视图，非必需）。

### 9.2 恢复步骤（文本记忆与系统）

```bash
# ① 克隆主库
git clone https://github.com/<owner>/<repo>.git mindseed
cd mindseed

# ② 校验完整性（应全部通过）
python3 99-系统/scripts/check_links.py            # 双链完整
git ls-files | grep user-profile || echo "✅ 隐私未入云"

# ③ 配置环境（Linux / 云端；Windows 见 §9.3）
export GH_TOKEN=<你的 token>

# ④ 首次唤醒自检
bash 99-系统/scripts/wake.sh
# 预期输出："🧠 记忆新鲜度：截至 <hash>（<date>）" + 读取指引

# ⑤ 按 wake 输出读取
#    SOUL.md → HOME.md → 按线程类型按需检索（见 99-系统/唤醒协议.md）
```

### 9.3 各 harness 接入（恢复指针）

唤醒指针只放「指针与纪律」，不放记忆内容。按 harness 规则位放置（模板见 `99-系统/scripts/唤醒指针模板.md`）：

| harness | 规则位 | 唤醒命令 |
|---|---|---|
| codex / 通用 Agent（POSIX） | 工作区根 `AGENTS.md` | `bash <REPO_DIR>/99-系统/scripts/wake.sh` |
| Claude Code | `CLAUDE.md`（可引 AGENTS.md） | 同上 |
| Trae（云端一次性沙箱） | 用户规则位 / 手动 | 手动唤醒：clone → `bash wake.sh`；或以 `mind-wake` skill 为载体 |
| Windows Agent | profile / patch 规则位 | `powershell -File <REPO_DIR>\99-系统\scripts\wake.ps1` |

**Windows 端机器前置（务必先做）**：

```bash
git config --global http.sslBackend openssl          # T3
git config --global http.proxy http://127.0.0.1:7897 # T4，按本机代理端口改
```

token 放 `%USERPROFILE%\.mindseed\ghToken.txt`（工作区外，T2）；`wake.ps1` 会自动兜底读取。

### 9.4 恢复图像层（仅启用图床时）

```bash
export GH_TOKEN=<token>
bash 99-系统/可选-图库双仓/scripts/vision.sh ls          # 列图库根，确认可访问
bash 99-系统/可选-图库双仓/scripts/vision.sh get <路径> /tmp/x.jpg
```

- 图库**不需要 clone**，按需 `get` 即可。
- 若换细粒度 PAT，**记得把图库仓库加入 contents 授权清单**，否则图库不可访问。

### 9.5 极端情况：远端也丢失

此时以本说明书 + 任意一处未丢失的副本为蓝本重建。重建优先级：

1. **文本骨架**（最小可运行集）：
   - `SOUL.md`、`HOME.md`、`mind.config` —— 人格与中枢；
   - `99-系统/` 三份规范 + 脚本（wake.sh / wake.ps1 / check_links.py / 唤醒指针模板）+ [[首次唤醒引导]]；
   - `90-模板/` 五份模板；
   - `记忆总览.base`；`.gitignore`；`.gitattributes`；`.github/workflows/guard.yml`。
2. **记忆内容**：按组补齐 `10–80` 各篇（优先从其它端副本汇合）。
3. **技能组**：从 `85-技能组/` 整目录恢复（vault 为唯一事实源）。
4. **图像层**：若启用，按 §9.4 接入；若丢失，人设图需重新生成。
5. **隐私档案**：`user-profile.md` **本就不在云上**，无法从仓库恢复，须由用户从库外备份 / 记忆重建。
6. **重建后自检**：跑 `check_links.py` 与 `wake.sh`，确认双链完整、隐私未入云、唤醒可用。

### 9.6 恢复验证清单

- [ ] `check_links.py` 输出 "✅ 双链完整"
- [ ] `git ls-files | grep user-profile` 无输出（隐私未入云）
- [ ] `wake.sh` / `wake.ps1` 能完成 pull 并报出新鲜度
- [ ] 启用图床时 `vision.sh ls` 能列出图库目录
- [ ] 新会话按唤醒指针能读 SOUL → HOME → 按需检索
- [ ] CI `guard.yml` 在 push 后转绿
